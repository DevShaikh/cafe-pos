# Architecture and Product Decisions

This file records decisions that should guide implementation. “Decision” means the intended rule; the implementation column calls out where current code differs. See [`pos-spec.md`](pos-spec.md) for detailed feature status and review findings.

| Topic                   | Decision                                                                                                                                   | Current implementation                                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Product purpose         | Locally run, single-cashier cafe POS focused on fast counter checkout.                                                                     | Next.js client, local Express API, SQLite product store, development Electron shell.                                                      |
| Currency                | PKR; user-facing values should consistently display as `PKR 1,200.00`.                                                                     | `formatPKR` formats paisa by dividing by 100; catalog currently passes an API rupee value directly, so card price units are inconsistent. |
| Money arithmetic        | Use integer paisa as the source of truth; do not use JS floating-point decimal prices in calculations.                                     | Product price is an API string, but cart converts it to `number`; checkout rounds `price * 100`. This needs alignment.                    |
| Tax                     | Fixed 8% during the initial checkout flow; make configurable only in a scoped settings phase.                                              | Hard-coded in `ReceiptPanel`; settings page is a placeholder.                                                                             |
| Payment                 | Manual cashier confirmation after receiving cash/transfer. Creating a receipt means UNPAID; only explicit confirmation changes it to PAID. | `markAsPaid` updates a local Zustand receipt and timestamp. No payment provider or backend endpoint.                                      |
| Order type              | `DINE_IN` and `TAKEAWAY` are labels only; they do not change price/tax.                                                                    | Stored on local receipt.                                                                                                                  |
| Receipt timing          | Generate/issue the receipt before payment; clearing the draft cart enables the next order.                                                 | Receipt is added to local order store and cart clears. The print selection path needs correction/validation.                              |
| Printing                | Use `react-to-print` with an 80mm receipt template as the first browser print integration.                                                 | Browser print flow is invoked; silent printer access, device selection, and robust lifecycle are not established.                         |
| Local order persistence | Preserve orders across reloads until server-side order persistence is implemented.                                                         | Zustand `persist` writes receipts and receipt counter to localStorage key `cafe-pos-orders`. This is local to a browser profile/device.   |
| Cart persistence        | Draft cart is transient; it resets after receipt generation.                                                                               | Zustand in-memory store; no persistence middleware.                                                                                       |
| State ownership         | TanStack Query owns remote server state; Zustand owns client interaction state.                                                            | Product list via Query; cart and receipts via Zustand.                                                                                    |
| Product API contract    | Price is a two-decimal string; nullable description/image URL, category, availability and ISO timestamps are part of the product response. | Express service maps Prisma Decimal price to a string; client Zod schema infers `Product`.                                                |
| Backend layering        | Express routes -> controllers -> services -> Prisma/database. Validate external input and return explicit errors.                          | Product-list flow follows these layers; no order API yet.                                                                                 |
| Database                | SQLite file with Prisma 7 and `better-sqlite3`; keep schema multi-file under `server/prisma/schema`.                                       | Product model and seed exist; orders are not in the database.                                                                             |
| UI theme                | Tailwind CSS v4 and semantic CSS variables; component colors should use tokens. Support light and dark themes.                             | Tokens and `next-themes` toggle are configured in the client.                                                                             |
| Product media           | Placeholders are acceptable until real product imagery is scoped.                                                                          | Product cards show a “No Image” placeholder.                                                                                              |
| User model              | Single cashier initially; no waiter accounts or authentication requirement in current workflow.                                            | Cashier/session display is static; login is a placeholder; no auth enforcement.                                                           |
| Scope boundaries        | No table management, reservations, kitchen slips, gateway, or inventory management in initial POS workflow.                                | These workflows are not implemented.                                                                                                      |

## Implementation priorities implied by these decisions

1. Correct unit conversion at the product card and establish integer-paisa data through the cart and receipt calculation.
2. Select the receipt created by the current checkout action reliably and make print state lifecycle depend on actual print callbacks.
3. Keep documentation and roadmap status aligned with shipped behavior; do not describe a placeholder as a completed feature.
4. Design server-side receipt persistence before replacing local persistence, retaining receipt item name and unit-price snapshots.
